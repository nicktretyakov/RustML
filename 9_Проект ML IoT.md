**ML IoT MVP**

<https://gitverse.ru/nicktretyakov1/interop_ml>

Полноценная edge-система мониторинга температуры с локальной ML-обработкой. ML-часть работает **локально на устройстве** (edge ML): Kalman-фильтрация + ensemble-детектор аномалий (несколько моделей обновляются параллельно через rayon). Всё организовано как конвейер (pipeline): чтение сенсора → пул воркеров обработки → агрегация и передача.
#### **1. Общая архитектура (многопоточный pipeline)**
Проект использует **три основных потока** (threads) и **каналы crossbeam-channel** для передачи данных без блокировок:

Поток — это как отдельный работник, который выполняет свою задачу параллельно с другими. В программе может быть несколько потоков, каждый из которых занимается своим делом одновременно.

**Пример:** Представьте кафе, где один работник принимает заказы (поток чтения сенсора), другой готовит кофе (воркеры обработки), а третий разносит готовые заказы (поток передачи). Все работают одновременно, не мешая друг другу.

Каналы — это способ передачи данных между потоками без блокировок. Один поток отправляет данные в канал, другой — получает их оттуда. Каналы бывают unbounded (без ограничения по размеру), то есть данные не теряются, даже если получатель временно не успевает их обрабатывать.

**Пример:** Представьте конвейер на заводе: один рабочий кладёт детали на ленту (отправляет в канал), другой берёт их с ленты (получает из канала). Лента может растягиваться, если деталей становится много, но ничего не теряется.

1. **Поток чтения сенсора** (device.spawn\_sensor\_thread):
   1. Читает температуру каждые read\_interval\_secs.
   1. Отправляет сырые значения в канал raw\_tx → raw\_rx.
1. **Пул воркеров обработки** (ProcessingPipeline::spawn, количество = worker\_count):
   1. Каждый воркер независимо получает сырые значения из raw\_rx.
   1. Применяет Kalman-фильтр. Это математический алгоритм, который помогает «сглаживать» шумные данные (например, температуру с датчика), чтобы получить более точное значение.

      **Пример:** Если у вас термометр на улице показывает то 20°, то 22°, то 19°, Kalman-фильтр поможет понять, что реальная температура около 20.5°.

   1. Обновляет **ensemble** моделей аномалий **параллельно** через rayon::par\_iter\_mut. Это набор разных алгоритмов, которые вместе определяют, какие данные являются аномальными (например, резкий скачок температуры).

      **Пример:** Представьте, что у вас три эксперта: один смотрит на график температуры, другой — на историю, третий — на погоду. Вместе они решают, нормальное ли значение или что-то пошло не так.

   1. Считает аномалии (атомарный AtomicU32 для глобального счётчика). Это специальный счётчик, который можно безопасно увеличивать из разных потоков, не боясь ошибок. Используется для подсчёта аномалий.

      **Пример:** Если несколько кассиров в магазине одновременно считают количество проданных товаров, им нужен общий счётчик, который не сбоит при одновременном доступе.

   1. Фильтрует аномалии и батчит нормальные значения. Это объединение нескольких данных в один пакет перед отправкой, чтобы уменьшить нагрузку на сеть.

      **Пример:** Вместо того, чтобы отправлять каждое значение температуры отдельно, вы ждёте, пока накопится 10 значений, и отправляете их все вместе.

   1. По заполнению батча отправляет агрегированное значение + текущий счётчик аномалий в канал agg\_tx.
1. **Поток передачи** (отдельный thread::spawn в main):
   1. Получает агрегированные пакеты из agg\_rx.
   1. Формирует JSON-пэйлоад и отправляет POST-запросом через reqwest. JSON — это удобный формат для передачи данных. POST-запрос — это способ отправить данные на сервер (например, на сайт или в облако).

      **Пример:** Вы заполняете форму на сайте и нажимаете «Отправить». Ваши данные упаковываются в JSON и отправляются на сервер через POST-запрос.

Это **классический producer-consumer pipeline** с несколькими consumers (воркеры). Каналы unbounded — данные не теряются при временных задержках. Это модель, где один поток (producer) создаёт данные, а другие потоки (consumers) их обрабатывают. В вашем примере:

- Поток чтения сенсора — producer (создаёт данные).
- Воркеры обработки — consumers (обрабатывают данные).

**Пример:** На фабрике один рабочий делает детали (producer), а несколько других собирают из них готовые изделия (consumers).
#### **2. Конфигурация (app\_[**config.rs**](http://config.rs/) + embedded defaults в [**main.rs**](http://main.rs/))**
- AppConfig — единая структура с вложенными конфигами и enum-вариантом для сенсора. Это как коробка с настройками для вашего проекта. Внутри неё лежат разные «ящички» (вложенные конфиги) — например, настройки для базы данных, для логов, для датчиков. А ещё есть переключатель (enum), который позволяет выбрать, какой именно датчик использовать — настоящий или симулятор.

  **Пример:** Представьте, что у вас есть умный дом. В AppConfig могут быть:

  - Настройки для термометра (датчик температуры)
  - Настройки для симулятора термометра (если настоящего нет под рукой)
  - Настройки для логов (куда и как сохранять данные)

Enum позволяет выбрать: «Использовать настоящий датчик» или «Использовать симулятор».

- Defaults встроены как строковый TOML (через File::from\_str) — проект запускается без config.toml. Если вы не создали файл с настройками (config.toml), программа всё равно запустится — у неё есть «заводские» настройки, прописанные прямо в коде. Эти настройки хранятся в виде текста в формате TOML (это такой удобный формат для конфигов, похожий на INI).

  **Пример:** Допустим, по умолчанию программа считает, что датчик температуры — это симулятор, а порог температуры — 25°C. Эти значения прописаны в коде как строка в формате TOML.

- При наличии config.toml или env-переменных (APP\_...) они переопределяют defaults. Если вы создадите файл config.toml или зададите переменные окружения (например, APP\_SENSOR\_TYPE=real), то программа будет использовать уже ваши настройки, а не заводские.
- config crate автоматически мержит источники и десериализует в AppConfig. Библиотека config сама собирает все настройки из разных мест (заводские, файл, переменные окружения), объединяет их и преобразует в удобную структуру AppConfig, с которой легко работать в коде.

  **Пример:**

  - Заводские настройки: симулятор, порог 25°C
  - Файл config.toml: настоящий датчик, порог 30°C
  - Переменная окружения: порог 35°C

Библиотека возьмёт самое приоритетное значение (переменная окружения) и создаст AppConfig с настоящим датчиком и порогом 35°C.

Это позволяет легко переключаться между симулятором и реальным DS18B20 без recompilation (только config). Вы можете в любой момент поменять, какой датчик использовать — просто изменив файл настроек или переменную окружения. Не нужно пересобирать программу!

**Пример:**

- Сегодня вы тестируете программу с симулятором — в config.toml прописан type = "simulator".
- Завтра вы подключили настоящий датчик DS18B20 — просто меняете type = "real" в config.toml, и программа уже работает с настоящим датчиком.
#### **3. Сенсорная часть (sensor/ модуль, DIP + фабрика)**
- Трейт TemperatureSensor: минимальный интерфейс (read() -> Result<f64>). **ISP** — клиент использует только нужный метод. Здесь TemperatureSensor — это трейт, который говорит: "Любой датчик температуры должен уметь делать read(), который возвращает результат в виде числа с плавающей запятой (f64) или ошибку".

  **Пример:** Представьте, что у вас есть пульт от телевизора. На нём есть кнопка "Включить". Не важно, какой у вас телевизор — Samsung или LG — главное, что у него есть метод "включиться". Так и здесь: не важно, какой датчик — главное, что он умеет read(). **ISP** - принцип проектирования, который говорит: "Не заставляйте клиента зависеть от методов, которые он не использует". То есть, если клиенту нужен только метод read(), не надо заставлять его работать с датчиком, у которого ещё 10 ненужных методов.

  **Пример:** Вы заказываете пиццу. Вам не нужен весь ресторан — вам нужен только повар, который умеет печь пиццу, и курьер, который умеет её привезти. Не надо заставлять вас общаться с бухгалтерией ресторана.

- Две реализации:
  - SimulatedTemperatureSensor: генерирует шумные данные.
  - Ds18b20Sensor: читает /sys/bus/w1/devices/... с retry и CRC-проверкой. 

    Это два разных датчика, которые реализуют один и тот же трейт TemperatureSensor, но работают по-разному.

    - **SimulatedTemperatureSensor** — это "виртуальный" датчик, который просто генерирует случайные данные (например, для тестов).
    - **Ds18b20Sensor** — это реальный датчик, который читает данные из файла в системе (например, /sys/bus/w1/devices/...), проверяет их на ошибки и повторяет попытку, если что-то пошло не так.

**Пример:** Представьте, что у вас есть два способа узнать температуру:

- Попросить друга сказать случайное число (симуляция).
- Посмотреть на настоящий термометр за окном (реальный датчик).
- SensorFactory::create: возвращает Arc<dyn TemperatureSensor> на основе app\_config.sensor. Это "фабрика", которая создаёт нужный датчик на основе настроек (app\_config.sensor). Она возвращает не конкретный тип датчика, а "упакованный" в Arc<dyn TemperatureSensor> объект.

  **Пример:** Вы заказываете машину в такси. Вам не важно, какая машина приедет — главное, что она умеет ездить. Так и здесь: фабрика возвращает датчик, который умеет read(), а какой именно — не важно. 

  **dyn TemperatureSensor** — это указатель на любой объект, который реализует трейт TemperatureSensor.

  **Arc** (Atomic Reference Counting) — это "умный указатель", который позволяет безопасно делиться объектом между разными потоками (например, чтобы несколько частей программы могли одновременно читать данные с датчика).

**Пример:** Представьте, что у вас есть книга, которую могут читать несколько человек одновременно. Arc — это как библиотекарь, который следит, чтобы книга не потерялась и не порвалась, пока её читают.

- Сенсор обёрнут в Arc — безопасно клонируется для потока чтения. Благодаря Arc, можно создать копию указателя на датчик и передать её в другой поток (например, для параллельного чтения данных). При этом не будет проблем с доступом к данным, потому что Arc следит за безопасностью.

  **Пример:** Вы даёте другу копию ключа от квартиры. Теперь вы оба можете заходить в квартиру, не мешая друг другу.
#### **4. Обработка данных — сердце ML-части (processing/)**
##### **4.1 Kalman-фильтр ([**kalman.rs**](http://kalman.rs/)) - математический инструмент, который помогает "очищать" данные от шума и предсказывать будущие значения на основе прошлых. Представьте, что у вас есть датчик температуры, который иногда выдаёт неточные показания (шум). Kalman-фильтр помогает получить более точное значение, учитывая как текущие, так и прошлые данные.**
**Пример:** Вы измеряете температуру на улице каждую минуту, но датчик иногда ошибается. Kalman-фильтр поможет сгладить эти ошибки и показать более правдоподобную температуру.

- Простая байесовская фильтрация шума.
- Каждый воркер имеет свой собственный KalmanFilter (stateful).
##### **4.2 Ensemble-детектор аномалий (anomaly/) - набор из нескольких моделей, которые одновременно ищут аномалии (необычные, подозрительные данные). Каждая модель работает по-своему, а потом они "голосуют" — если большинство моделей сказало, что данные подозрительные, то это аномалия.**
**Реализации:**

- **SimpleEWADetector:** следит за средним значением и разбросом данных (как далеко данные отклоняются от среднего).
- **ZScoreDetector:** считает, насколько сильно данные отклоняются от среднего в стандартных отклонениях.

**Пример:** Вы следите за трафиком на сайте. Обычно у вас 100 посетителей в час, но вдруг стало 10 000. Ensemble-детектор заметит это как аномалию, потому что несколько моделей одновременно скажут: "Это необычно!"

- Трейт AnomalyModel: update(value) -> bool (аномалия?) + reset.
- Реализации:
  - SimpleEWADetector: экспоненциальное скользящее среднее + дисперсия (online Gaussian).
  - ZScoreDetector: классический Z-score на накопленных данных.
- EnsembleDetector: хранит вектор Box<dyn AnomalyModel>.
  - update: **параллельно** (rayon::par\_iter\_mut) обновляет все модели.
  - Majority vote для финального решения (расширяемо: можно weighted vote).
  - Это **настоящая многопроцессная ML**: несколько моделей работают одновременно на разных ядрах.
##### **4.3 Pipeline воркеров ([**pipeline.rs**](http://pipeline.rs/)) - как конвейер на заводе: каждый рабочий (воркер) выполняет свою часть работы с данными. У каждого воркера есть:**
- свой Kalman-фильтр (очищает данные),
- свой детектор аномалий (ищет подозрительные данные),
- буфер для накопления данных (батчинг).

**Как работает:**

- Воркер получает данные, очищает их, проверяет на аномалии.
- Если аномалий нет, данные накапливаются в буфере.
- Когда буфер заполняется, воркер отправляет среднее значение и счётчик аномалий.

**Пример:** У вас несколько касс в магазине. Каждая касса (воркер) считает покупки, проверяет подозрительные транзакции, а потом отправляет отчёт о средней сумме чека и количестве подозрительных операций.

- Каждый воркер:
  - Имеет свой KalmanFilter + EnsembleDetector + буфер для батчинга.
  - Атомарно инкрементирует глобальный счётчик аномалий (AtomicU32).
  - Отбрасывает батчи с аномалиями.
  - По заполнению батча отправляет среднее + текущий глобальный счётчик.

**Многопроцессность**: несколько задач выполняются одновременно на разных ядрах процессора:

- несколько воркеров работают параллельно,
- внутри каждого воркера детектор аномалий тоже использует параллелизм (rayon).

**Пример:** Представьте, что у вас 4 кассы (воркера) и каждая может одновременно проверять транзакции по нескольким правилам (модели детектора). Всё работает быстрее, потому что задачи распределены.

- worker\_count воркеров (по умолчанию = числу ядер).
- rayon внутри ensemble — дополнительный параллелизм на уровне моделей.
#### **5. Передача данных (transmission/)**
- HttpTransmitter: blocking reqwest клиент с таймаутом. Это модуль, который отправляет данные по интернету (по протоколу HTTP). Проще говоря, это как почтальон, который берёт ваше письмо (данные) и относит его по нужному адресу в интернете.

  **Пример:** Представьте, что у вас дома стоит датчик температуры. Он измеряет температуру каждую минуту. Чтобы эти данные попали на сервер (например, на сайт, где отображается погода), нужен кто-то, кто их отправит. Вот этим и занимается HttpTransmitter. **reqwest** — это популярная библиотека на языке Rust для работы с HTTP-запросами (то есть для отправки и получения данных по интернету). **blocking** — означает, что программа будет ждать ответа от сервера, прежде чем продолжить работу. То есть, пока данные не отправятся и не придёт ответ, программа как бы «замирает» на этом шаге.

**Пример:** Вы звоните другу и ждёте, когда он ответит. Пока он не возьмёт трубку, вы не можете положить её и заняться чем-то другим. Так же и здесь: пока данные не отправятся и не придёт ответ, программа не перейдёт к следующему шагу.

Таймаут — это ограничение по времени. Если сервер не отвечает слишком долго, программа не будет ждать бесконечно, а прекратит попытку и, например, сообщит об ошибке.

**Пример:** Вы звоните другу, но он не берёт трубку. Вы ждёте 30 секунд, а потом кладете трубку и думаете: «Наверное, он занят». Здесь 30 секунд — это таймаут.

- Формирует JSON с температурой, timestamp, device\_id и общим счётчиком аномалий. Программа собирает данные в специальный формат — **JSON** (это удобный способ записывать данные, который понимают почти все программы). В этом JSON-е содержатся:
  - **температура** — например, 25.5°C;
  - **timestamp** — метка времени (когда было сделано измерение), например, "2026-02-05 14:30:00";
  - **device\_id** — уникальный идентификатор устройства (например, "sensor\_123");
  - **общий счётчик аномалий** — сколько раз температура была необычной (например, слишком высокой или низкой).
#### **6. Устройство и запуск ([**device.rs**](http://device.rs/) + [**main.rs**](http://main.rs/))**
- EdgeDevice: композиция сенсора + канала для сырых данных. Это устройство (например, датчик температуры или камера), которое собирает данные (сырые данные — raw data) и отправляет их дальше по специальному "каналу" (как труба, по которой текут данные).

  **Пример:** Представьте умный термометр на улице. Он измеряет температуру (сенсор) и отправляет эти данные на сервер (канал). Канал — это как дорога, по которой едут машины с данными.

- main: wiring всех компонентов, запуск потоков, graceful shutdown через Ctrl+C (дропаем клоны Sender — канал закроется, воркеры завершатся). Это главная часть программы, где все детали (сенсоры, каналы, обработчики) соединяются между собой, как провода в электрической схеме.

  **Пример:** Как если бы вы собирали конструктор: берёте мотор, батарейку, кнопку и соединяете их проводами, чтобы всё заработало.

**ML IoT ООП**

- Используется **композиция над наследованием** (GoF-рекомендация).
- **Полиморфизм** достигается через **trait objects** (dyn Trait) и **статический полиморфизм** (generics где возможно).
#### **1. Инкапсуляция (Encapsulation)**
- Поля структур по умолчанию приватные (видны только внутри модуля).
- Публичные методы реализуются через impl.

**Примеры в проекте**:

- KalmanFilter (processing/[kalman.rs](http://kalman.rs/)):

  pub struct KalmanFilter {

  `    `estimate: f64,      // приватные поля

  `    `error\_cov: f64,

  `    `process\_noise: f64,

  `    `measurement\_noise: f64,

  }

  impl KalmanFilter {

  `    `pub fn new(...) -> Self { ... }  // конструктор

  `    `pub fn update(&mut self, measurement: f64) -> f64 { ... }  // единственный публичный метод

  }

  Внутреннее состояние (оценка, ковариация) скрыто, доступ только через update.

- EnsembleDetector (processing/anomaly/[mod.rs](http://mod.rs/)):

  pub struct EnsembleDetector {

  `    `models: Vec<Box<dyn AnomalyModel>>,  // приватный вектор моделей

  }

  Клиент не может напрямую модифицировать модели — только через update и reset.

- HttpTransmitter (transmission/[http.rs](http://http.rs/)): клиент reqwest::Client инкапсулирован, конфигурация скрыта.
#### **2. Абстракция (Abstraction)**
**Ключевые абстракции**:

- TemperatureSensor (sensor/[mod.rs](http://mod.rs/)):

  pub trait TemperatureSensor: Send + Sync + 'static {

  `    `fn read(&self) -> Result<f64, SensorError>;

  }

- AnomalyModel (processing/anomaly/[mod.rs](http://mod.rs/)):

  pub trait AnomalyModel: Send + Sync {

  `    `fn update(&mut self, value: f64) -> bool;

  `    `fn reset(&mut self);

  }

  Минимальный контракт для моделей аномалий.
#### **3. Полиморфизм (Polymorphism)**
- **Статический полиморфизм** (compile-time): через generics (используется редко в проекте).
- **Динамический полиморфизм** (runtime): через **trait objects** (dyn Trait в Box/Arc).

**Реализация динамического полиморфизма**:

- Сенсоры:

  // Фабрика возвращает trait object

  pub fn create(config: &AppConfig) -> Arc<dyn TemperatureSensor> { ... }

  // В EdgeDevice

  sensor: Arc<dyn TemperatureSensor>,

  Один и тот же код работает с SimulatedTemperatureSensor или Ds18b20Sensor без условных веток (Liskov Substitution Principle).

- Модели аномалий (самое сложное место — многопроцессная ML):

  pub struct EnsembleDetector {

  `    `models: Vec<Box<dyn AnomalyModel>>,  // вектор разных моделей

  }

  impl EnsembleDetector {

  `    `pub fn update(&mut self, value: f64) -> (u32, bool) {

  `        `let flags: Vec<bool> = self.models.par\_iter\_mut()  // ПАРАЛЛЕЛЬНО через rayon

              .map(|model| model.update(value))

              .collect();

  `        `// majority vote

  `    `}

  }

  **Полиморфизм + многопроцессность**: разные модели (SimpleEWADetector, ZScoreDetector, будущие ONNX-модели) хранятся в одном векторе и вызываются полиморфно. par\_iter\_mut обеспечивает **параллельное** обновление на разных ядрах — это **многопроцессная обработка ML** в чистом виде.
#### **4. Наследование (Inheritance) → Композиция**
**не имеет наследования**, но проект использует **композицию** (GoF: "предпочтительнее наследования").

**Примеры композиции**:

- Processor в pipeline (внутренний struct воркера):

  struct Processor {

  `    `kalman: KalmanFilter,              // композиция фильтра

  `    `anomaly: EnsembleDetector,         // композиция ensemble-детектора

  `    `buffer: Vec<f64>,                  // буфер для батчинга

  `    `batch\_size: usize,

  }

  Объект обработки = фильтр + детектор + буфер.

- EdgeDevice:

  pub struct EdgeDevice {

  `    `sensor: Arc<dyn TemperatureSensor>,  // композиция сенсора

  `    `raw\_tx: Sender<f64>,

  `    `config: AppConfig,

  }

- EnsembleDetector: композиция множества моделей в вектор.

Это **Delegation Pattern**: поведение делегируется вложенным объектам.
#### **Итоговая связь ООП с многопроцессной ML и SOLID**
- **Многопроцессная ML** реализована через **полиморфизм + композицию + rayon**:
  - Ensemble — композиция разных моделей.
  - Trait object позволяет хранить разнородные модели в одном контейнере.
  - par\_iter\_mut — параллельное выполнение update на разных моделях (многопроцессность на уровне ядер CPU).
- **SOLID** делает ООП расширяемым:
  - Новый сенсор → новая реализация трейта + ветка в enum.
  - Новая тяжёлая ML-модель (ONNX/Burn) → реализация AnomalyModel + добавление в вектор.
  - Нет нарушения инкапсуляции или зависимостей.

**Подробное объяснение реализации принципов SOLID в коде**
#### **1. Single Responsibility Principle (SRP) — Принцип единственной ответственности**
**Реализация в проекте**:

- **Модульная структура**: Каждый модуль (sensor/, processing/, transmission/, device/) отвечает ровно за одну доменную область.
  - sensor/: только чтение температуры (абстракция + реализации).
  - processing/: только фильтрация и детекция аномалий (Kalman + ensemble + батчинг).
  - transmission/: только отправка данных по HTTP.
  - device/: только координация сенсора и канала (композиция).
- **Структуры и трейты**:
  - KalmanFilter: только байесовская фильтрация шума.
  - EnsembleDetector: только управление ensemble-моделями и majority vote (не знает о батчинге или передаче).
  - Каждая модель аномалий (SimpleEWADetector, ZScoreDetector): только своя статистика и детекция.
- **В многопроцессной части**:
  - Воркеры в ProcessingPipeline: каждый отвечает только за обработку одного сырых значения (фильтр → детекция → батчинг).
  - Глобальный счётчик аномалий — отдельный AtomicU32, не смешивается с логикой моделей.

**Преимущества в проекте**: Изменение ML-логики (добавить ONNX-модель) не затронет сенсор или передачу. Это критично для edge: минимизация recompilation и размера бинарника.
#### **2. Open-Closed Principle (OCP) — Принцип открытости/закрытости**
**Реализация в проекте**:

- **Через трейты и композицию** (не наследование):
  - TemperatureSensor: добавить новый сенсор (например, BME280) — новая структура + impl трейта + ветка в SensorFactory::create. Существующий код (EdgeDevice) не меняется.
  - AnomalyModel + EnsembleDetector: ключевая часть для **многопроцессной ML**.
    - Расширение: добавить тяжёлую модель (IsolationForest через linfa или автоэнкодер ONNX через tract):

      Box::new(OnnxAnomalyModel::load("model.onnx"))

      — просто вставить в EnsembleDetector::new(vec![...]).

    - update использует par\_iter\_mut (rayon) — параллелизм сохраняется автоматически для новых моделей.
    - Majority vote — параметризуемо (можно weighted ensemble без изменения update).
- **Конфигурация**: AppConfig с enum — расширение сенсора через новый вариант enum, без изменения десериализации.
- **Pipeline**: Добавление нового этапа обработки (например, дополнительный фильтр) — вставить в Processor как композицию, без изменения каналов.

**Преимущества**: Проект "закрыт" (стабильный pipeline), но открыт для новых ML-моделей — идеально для edge-AI эволюции (от лёгких статистических к тяжёлым нейронным сетям).
#### **3. Liskov Substitution Principle (LSP) — Принцип подстановки Барбары Лисков**
**Реализация в проекте**:

- **Trait objects** гарантируют LSP:
  - Любая реализация TemperatureSensor (Simulated... или Ds18b20...) возвращает Result<f64> с одинаковыми семантикой ошибок.
  - Клиент (EdgeDevice::spawn\_sensor\_thread) вызывает [sensor.read](http://sensor.read/)() — поведение идентично независимо от реализации (симуляция или реальный hardware).
- **AnomalyModel**:
  - Все модели (SimpleEWADetector, ZScoreDetector, будущие ONNX) возвращают bool (аномалия?) и имеют reset.
  - EnsembleDetector::update работает с любой комбинацией — замена модели не нарушает majority vote или параллелизм (par\_iter\_mut).

**Преимущества в многопроцессной ML**: Воркеры могут использовать разные ensemble (теоретически), но LSP гарантирует, что любой EnsembleDetector ведёт себя предсказуемо при параллельном вызове.
#### **4. Interface Segregation Principle (ISP) — Принцип разделения интерфейсов**
**Реализация в проекте**:

- Трейты **максимально узкие**:
  - TemperatureSensor: только read() — ничего лишнего (нет конфигурации, нет закрытия).
  - AnomalyModel: только update + reset — воркеры не зависят от внутренних статистик моделей.
- Нет "жирных" интерфейсов: вместо одного большого трейта для обработки — композиция мелких (KalmanFilter отдельно, EnsembleDetector отдельно).

**Преимущества**:

- Воркеры зависят только от нужного (например, не знают о HTTP).
- Легко тестировать: mock-реализация TemperatureSensor для unit-тестов обработки.
#### **5. Dependency Inversion Principle (DIP) — Принцип инверсии зависимостей**
**Реализация в проекте**:

- **Фабрики и trait objects**:
  - SensorFactory::create → Arc<dyn TemperatureSensor>: EdgeDevice (высокоуровневый) зависит от абстракции, а не от Ds18b20Sensor.
  - ProcessingPipeline использует EnsembleDetector с Box<dyn AnomalyModel> — детали моделей (EWMA или ONNX) инвертированы.
- **Конфигурация**: main инжектит зависимости через фабрики и конфиг — нет хардкода.
- **Многопроцессность**: Каналы (Sender/Receiver) — абстракция коммуникации; воркеры не знают, кто производитель/потребитель.

**Преимущества**:

- Замена реализации (симулятор ↔ реальный сенсор) — только config.toml.
- Добавление тяжёлой ML-модели — без изменения pipeline (DIP + OCP).

**Конкурентность**

Проект реализует **высокопроизводительную конкурентную архитектуру** на основе **многопоточного конвейера (pipeline)** с элементами **параллелизма данных** (data parallelism) и **параллелизма задач** (task parallelism). Это классический паттерн **producer-consumer** с несколькими consumers, расширенный для **многопроцессной ML-обработки** (параллельное обновление ensemble-моделей аномалий на разных ядрах CPU через rayon).

- **std::thread** — для долгоживущих потоков (сенсор, передача, пул воркеров).
- **crossbeam-channel** — высокопроизводительные многопроизводительные каналы (unbounded MPMC — multi-producer multi-consumer).
- **rayon** — для параллелизма внутри одного потока (параллельное обновление моделей в ensemble).
- **std::sync::atomic** — для безопасного глобального счётчика аномалий.
- **Arc** — для безопасного совместного владения (сенсор, конфиг, счётчик).

Разберём реализацию по уровням и компонентам.
#### **1. Общая модель конкурентности: многопоточный pipeline (producer → multiple consumers → consumer)**
Проект использует **три логических этапа**, соединённых каналами:

[Поток сенсора] → (raw\_tx / raw\_rx) → [Пул воркеров обработки (N потоков)] → (agg\_tx / agg\_rx) → [Поток передачи]

- **Производитель (producer)**: один поток сенсора — генерирует сырые показания температуры.
- **Потребители-посредники (intermediate consumers)**: пул из worker\_count потоков (по умолчанию ~ числу ядер) — обрабатывают данные (ML-фильтрация и детекция).
- **Финальный потребитель**: один поток передачи — отправляет агрегированные данные по HTTP.

**Каналы** (crossbeam\_channel::unbounded):

- raw\_tx / raw\_rx: MPMC-канал для сырых значений (f64).
  - Один producer (сенсор).
  - Множество consumers (воркеры).
- agg\_tx / agg\_rx: MPMC-канал для агрегированных пакетов ((f64, u32) — средняя температура + счётчик аномалий).
  - Множество producers (воркеры).
  - Один consumer (передача).

**Преимущества**:

- **Буферизация**: unbounded каналы предотвращают блокировку сенсора при временных задержках в обработке/передаче.
- **Масштабируемость**: воркеры распределяют нагрузку по ядрам (особенно важно для тяжёлых ML-моделей).
- **Связь с SOLID**:
  - **SRP**: каждый поток — одна ответственность.
  - **DIP**: каналы — абстракция коммуникации, потоки зависят от Sender/Receiver, а не от конкретных реализаций.
#### **2. Поток чтения сенсора ([**device.rs**](http://device.rs/) + EdgeDevice::spawn\_sensor\_thread)**
- **Реализация**:

  thread::spawn(move || loop {

  `    `match sensor.read() {  // полиморфный вызов (dyn TemperatureSensor)

  `        `Ok(temp) => raw\_tx.send(temp),

  `        `Err(e) => error!(...),

  `    `}

  `    `thread::sleep(interval);

  });

- **Конкурентность**:
  - Независимый поток, не блокирует основной.
  - Arc<dyn TemperatureSensor> — безопасно клонируется для потока.
  - raw\_tx.clone() — каждый send увеличивает счётчик (MPMC).
- **Интеграция с ООП**:
  - Полиморфизм: вызов read() работает с любой реализацией сенсора (LSP).
  - Композиция: EdgeDevice владеет сенсором и каналом.
#### **3. Пул воркеров обработки — основная многопоточная часть (processing/[**pipeline.rs**](http://pipeline.rs/))**
- **Запуск пула**:

  for \_ in 0..config.worker\_count {

  `    `let raw\_rx = raw\_rx.clone();  // MPMC

  `    `let agg\_tx = agg\_tx.clone();

  `    `let total\_anomalies = total\_anomalies.clone();  // Arc<AtomicU32>

  `    `thread::spawn(move || { ... });

  }

- **Внутри каждого воркера**:
  - Stateful обработчик (Processor):
    - Собственный KalmanFilter (не делится — thread-safe по дизайну).
    - Собственный EnsembleDetector (с вектором моделей).
    - Буфер для батчинга.
  - Цикл:

    loop {

    `    `match raw\_rx.recv() {  // блокирующий recv — эффективно при нагрузке

    `        `Ok(raw) => {

    `            `let filtered = processor.kalman.update(raw);

    `            `let (new\_anoms, is\_anomaly) = processor.anomaly.update(filtered);  // здесь параллелизм!

    `            `total\_anomalies.fetch\_add(new\_anoms, Ordering::Relaxed);

    `            `if !is\_anomaly { buffer.push(...); if full → send avg + total }

    `        `}

    `        `Err(\_) => break,  // канал закрыт — graceful shutdown

    `    `}

    }

- **Глобальный счётчик аномалий**:

  let total\_anomalies = Arc::new(AtomicU32::new(0));

  - Атомарный, lock-free — безопасно из множества потоков.
  - fetch\_add + load — минимальная overhead.

**Связь с SOLID**:

- **OCP/DIP**: каждый воркер — независимая единица; добавление новой модели в ensemble не требует изменения воркера.
#### **4. Параллелизм внутри обработки: многопроцессная ML в ensemble (processing/anomaly/[**mod.rs**](http://mod.rs/))**
Это **самая сложная часть конкурентности** — **data parallelism** внутри одного воркера.

- EnsembleDetector::update:

  let flags: Vec<bool> = self.models.par\_iter\_mut()  // rayon!

      .map(|model| model.update(value))

      .collect();

- **rayon::par\_iter\_mut**:
  - Автоматически распределяет итерации по пулу потоков rayon (глобальный thread pool, по умолчанию = числу ядер).
  - **Многопроцессность**: несколько моделей обновляются **параллельно** на разных ядрах для одного значения.
  - Требования: модели Send + Sync (все реализации в проекте — stateless или с внутренним mutex-free состоянием).

**Почему это многопроцессная ML**:

- При тяжёлых моделях (например, ONNX-инференс через tract или автоэнкодер через burn):
  - Каждая модель может выполнять вычисления на CPU/GPU.
  - par\_iter\_mut распараллелит инференс → реальный параллельный ensemble на edge-устройстве.

**Связь с ООП**:

- Полиморфизм: Box<dyn AnomalyModel> — разные модели в одном векторе.
- Композиция: ensemble = вектор объектов.
#### **5. Поток передачи ([**main.rs**](http://main.rs/))**
- Простой consumer:

  thread::spawn(move || while let Ok((temp, anomalies)) = agg\_rx.recv() { transmit... });

- Блокирующий recv — эффективно ждёт данные.
#### **6. Graceful shutdown и безопасность**
- **Ctrl+C**:

  let agg\_tx\_for\_shutdown = agg\_tx.clone();

  ctrlc::set\_handler(move || drop(agg\_tx\_for\_shutdown.clone()));

  - Дроп клона → уменьшает счётчик senders.
  - Когда все senders дропнуты → recv() в воркерах и передаче возвращает Err → выход из циклов.
- **Безопасность**:
  - Нет Mutex/RwLock — только атомики и каналы (lock-free где возможно).
  - Arc для совместного владения immutable/stateful данных.
  - Send + Sync на трейтах — гарантирует thread-safety.
#### **Итог: Почему конкурентность максимально сложная и интегрированная**
- **Уровни параллелизма**:
  - Task parallelism: отдельные потоки для этапов pipeline.
  - Data parallelism: пул воркеров для обработки потока данных.
  - Fine-grained parallelism: rayon внутри ensemble для параллельного инференса моделей.
