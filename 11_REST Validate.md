# REST Validate MVP
https://dzen.ru/a/aQDOLODTCk0ji9SO

Данный модуль для проекта позволяет достичь нужного качества данных в json, классифицировать и структурировать данные.

# REST Validate ООП
В коде определены несколько структур, которые представляют сущности предметной области:

    • ComplexData — основные данные, содержат идентификатор, имя, вектор признаков, опциональные метки, вложенный словарь и временную метку.

    • NestedData — вложенные данные, содержат значение, категорию и подпризнаки.

    • SimpleKNN — классификатор k-ближайших соседей, хранит обучающие признаки, метки и параметр k.

    • SimpleDecisionTree — очень простое дерево решений, хранит порог, индекс признака и метки для двух ветвей.

Каждая структура инкапсулирует связанные данные. 
Например, SimpleKNN содержит все необходимое для работы алгоритма: обучающую выборку и гиперпараметр.

Методы

Для структур определены методы через блоки impl. Это аналог методов класса в ООП. 
Рассмотрим примеры:

SimpleKNN

`impl SimpleKNN {

    fn new(k: usize) -> Self { ... }          // конструктор

    fn fit(&mut self, features: Vec<Vec<f64>>, labels: Vec<usize>) { ... }

    fn predict(&self, features: &[Vec<f64>]) -> Vec<usize> { ... }

    fn euclidean_distance(&self, a: &[f64], b: &[f64]) -> f64 { ... }

}`

    • new — статический метод, создающий экземпляр (конструктор).
    • fit — изменяет состояние объекта (&mut self), загружая обучающие данные.
    • predict — использует текущее состояние для предсказания (&self).
    • euclidean_distance — вспомогательный метод, скрывающий детали вычисления.
Аналогично для SimpleDecisionTree определены методы new, fit, predict, а также вспомогательные calculate_impurity, gini_impurity, majority_vote. 


# Инкапсуляция
#[derive(...)] публичные для сериализации. Однако сама идея инкапсуляции сохраняется: методы предоставляют интерфейс для работы с объектом, скрывая внутреннюю реализацию.
 Например, пользователь SimpleKNN вызывает fit и predict, не зная, как именно хранятся данные или вычисляется расстояние.

Пользовательские трейты

Перечисление ValidationError реализует трейты:

    • From<io::Error> и From<serde_json::Error> — позволяют автоматически преобразовывать ошибки ввода-вывода и JSON в тип ValidationError. Это пример полиморфизма: функции, ожидающие Result<T, ValidationError>, могут использовать оператор ? с разными типами ошибок.

    • std::fmt::Display — определяет, как ошибка будет выводиться.

    • std::error::Error — маркерный трейт, позволяющий использовать ValidationError везде, где ожидается тип ошибки (например, в Box<dyn Error>).

Внешние трейты

Структуры ComplexData и NestedData используют serde::Serialize и serde::Deserialize. 
Это тоже проявление полиморфизма: функции serde_json::from_str и serde_json::to_string работают с любым типом, реализующим эти трейты.

Композиция объектов

Объекты могут содержать другие объекты.
 Например, ComplexData содержит HashMap<String, NestedData>, где значения — тоже структуры.
 Это классическая композиция, позволяющая строить иерархии данных.

Перечисления

ValidationError — это перечисление, которое может быть либо ошибкой ввода-вывода, либо ошибкой JSON.
 Это альтернатива наследованию: вместо создания подклассов мы определяем варианты, каждый из которых может содержать связанные данные.


# SOLID
**Single Responsibility Principle — SRP**

    • Структуры данных ComplexData и NestedData отвечают исключительно за хранение информации и её сериализацию/десериализацию (благодаря derive-атрибутам).

    • Перечисление ValidationError инкапсулирует только ошибки, возникающие при чтении файлов и парсинге JSON. Оно реализует стандартные трейты (From, Display, Error) для удобной работы с ошибками.

    • Функция read_json_file отвечает только за чтение и десериализацию JSON-файла построчно.

    • Функция extract_features выполняет только извлечение признаков и простейшее кодирование меток.

    • Функция normalize_features занимается исключительно нормализацией числовых признаков.

    • Структуры SimpleKNN и SimpleDecisionTree реализуют каждый свой алгоритм машинного обучения (kNN и дерево решений) со всем необходимым поведением.

    • Функция validate_data отвечает за ансамблевую проверку данных с использованием двух моделей.

    • Функция detect_anomalies предназначена только для выявления аномалий на основе расстояний.

    • main координирует общий поток выполнения: чтение,валидацию и вывод результатов.

Вывод: Принцип единственной ответственности соблюдается практически везде. Каждая структурная единица имеет одну чёткую цель.

**Open-Closed Principle — OCP**

В текущей реализации есть как соблюдение, так и нарушение этого принципа.

Соблюдение:

    • Добавление нового типа данных (например, OtherData) не потребует изменения существующих структур, если он будет соответствовать ожидаемому интерфейсу (например, сериализуемости).

    • Можно легко добавить новую функцию (например, другую нормализацию), не трогая существующие.

Нарушение по причине встраивания данного модуля в существующий проект:

    • Функция validate_data жёстко завязана на конкретные типы SimpleKNN и SimpleDecisionTree. Если мы захотим добавить третий классификатор (например, логистическую регрессию), нам придётся модифицировать тело validate_data, дописывая в него вызовы нового классификатора. Это нарушает OCP.

    • Аналогично, если потребуется использовать другую метрику расстояния в detect_anomalies, придётся изменять код этой функции.

Как можно улучшить:

Ввести общий трейт (интерфейс) для классификаторов, например:

`trait Classifier {

    fn fit(&mut self, features: &[Vec<f64>], labels: &[usize]);

    fn predict(&self, features: &[Vec<f64>]) -> Vec<usize>;

}`

Тогда validate_data могла бы принимать срез объектов, реализующих Classifier, и работать с ними единообразно.
 Новые классификаторы добавлялись бы без изменения validate_data.

**Liskov Substitution Principle — LSP**

В коде нет явного наследования, но есть перечисление ValidationError, которое можно рассматривать как сумму типов (sum type).
 Любая функция, работающая с ValidationError, должна корректно обрабатывать оба варианта — это обеспечивается сопоставлением с образцом (match) или методами трейтов, что гарантирует подстановку.

В остальном, поскольку отсутствует полиморфизм подтипов, LSP напрямую не применяется. 
Однако если бы мы ввели трейт Classifier, реализации должны были бы удовлетворять контракту: любой классификатор должен корректно работать в контексте, ожидающем Classifier (например, в validate_data).
 В текущем коде такой проверки нет.

**Interface Segregation Principle — ISP**

    • Структуры SimpleKNN и SimpleDecisionTree предоставляют ровно те методы, которые нужны для их использования: new, fit, predict, а также внутренние вспомогательные методы. Никаких избыточных публичных методов нет.

    • Функция validate_data использует только fit и predict — именно тот минимум, который требуется для ансамбля.

    • Стандартные трейты (Serialize, Deserialize, From, Display, Error) требуют реализации минимального набора функций, и они реализованы именно так.

**Dependency Inversion Principle — DIP**

В коде этот принцип нарушен наиболее явно поскольку это отдельный модуль:

    • Функция validate_data (верхний уровень) напрямую зависит от конкретных реализаций SimpleKNN и SimpleDecisionTree (нижний уровень). Вместо зависимости от абстракции (трейта Classifier) она жёстко привязана к деталям.

    • Аналогично, main напрямую вызывает конкретные функции (read_json_file, extract_features, normalize_features), хотя мог бы работать через абстракции (например, трейты для чтения данных, извлечения признаков и нормализации). Однако для небольших программ это допустимо, но с точки зрения DIP это зависимость от деталей.

Как можно улучшить:

    • Определить трейт DataReader, FeatureExtractor, Normalizer и передавать их в main через зависимости (например, через аргументы функций или структуры конфигурации).

    • Для классификаторов, как уже упоминалось, ввести трейт и использовать его в validate_data.

Конкурентность не используется
    • Код представляет собой модуль для встраивания.
    • Не предусмотрена производительность и масштабируемость.
