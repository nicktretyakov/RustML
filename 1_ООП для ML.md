# ﻿**Полиморфизм**

*Зачем использовать полиморфизм в ML?:*

Чтобы создать полноценную интеграцию с библиотеками ML, такими как ndarray, tch-rs (bindings для PyTorch), burn, linfa.

- **Полиморфизм** — В контексте Burn: вы пишете код, который работает с любым бэкендом (например, для GPU или CPU), не зная заранее, какой именно бэкенд будет использоваться.
- **Мутабельность** — Позволяет или не позволяет менять бэкенд.

В RUST ML полиморфизм часто реализуется через трейты, а мутабельность влияет на то, какие методы можно вызывать.

Представьте, что у вас есть два бэкенда:

- CpuBackend — выполняет операции на процессоре.
- GpuBackend — выполняет операции на видеокарте.

Оба реализуют один и тот же trait Backend, но внутри работают по-разному.

Trait в Rust — это способ описать, какие методы и свойства должен иметь какой-то тип (например, структура или перечисление). Похоже на интерфейсы в других языках программирования.

**Пример:** Представьте, что у вас есть trait *Языковая\_*модель с методом говорить(). Любой тип, который реализует этот trait, должен уметь "говорить":

trait Языковая\_модель {

`fn говорить(&self);

}

struct Пользователь

impl Языковая\_модель for Пользователь {

`    `fn говорить(&self) {

`        `println!("Запись!");

`    `}

}`

Здесь *Пользователь* реализует trait *Языковая\_*модель и теперь может "говорить".

### **Примеры кода для Backend trait в Burn**
В библиотеке **Burn** полиморфизм над бэкендами реализуется через trait burn::prelude::Backend (или burn::tensor::backend::Backend). Это центральный trait, который определяет типы тензоров, устройства и базовые операции. Большинство кода в Burn использует **generic**, что позволяет переключать бэкенд на уровне типов (compile-time) без изменения логики модели. Означает, что выбор бэкенда происходит при компиляции программы, а не во время её выполнения. Это делает программу быстрее и надёжнее. 

**Пример:** Если вы написали код с generic и указали тип CpuBackend, то компилятор сгенерирует код именно для CPU, а не будет решать это во время работы программы.

Generic позволяют писать код, который работает с разными типами данных, не дублируя логику. В Burn это используется, чтобы один и тот же код модели работал с разными бэкендами.

**Пример:** Функция, которая работает с любым типом, реализующим Backend:

```fn train\_model<B: Backend>(model: Model<B>, data: Tensor<B>) {

`    `// Обучение модели

}```

Здесь B — это обобщённый тип, который может быть и CpuBackend, и GpuBackend Вы можете вызвать эту функцию с разными бэкендами, не меняя код:

`let cpu\_model: Model<CpuBackend> = ...;

let gpu\_model: Model<GpuBackend> = ...;

train\_model(cpu\_model, cpu\_data);

train\_model(gpu\_model, gpu\_data);`

#### **1. Определение trait Backend (упрощённо из документации Burn)**
use burn::tensor::backend::{DeviceOps, Element, TensorMetadata, QTensorPrimitive};

```pub trait Backend:

`    `Sized

`    `+ Clone + Default + Send + Sync + Debug + 'static

{

`    `type Device: DeviceOps;

`    `type FloatTensorPrimitive: TensorMetadata + 'static;

`    `type FloatElem: Element;

`    `type IntTensorPrimitive: TensorMetadata + 'static;

`    `type IntElem: Element;

`    `type BoolTensorPrimitive: TensorMetadata + 'static;

`    `type BoolElem: Element;

`    `type QuantizedTensorPrimitive: TensorMetadata + QTensorPrimitive + 'static;

`    `fn name(device: &Self::Device) -> String;

`    `fn seed(device: &Self::Device, seed: u64);

`    `// Дополнительные provided методы (ad\_enabled, sync и т.д.)

`    `fn ad\_enabled() -> bool { false }

`    `fn sync(\_device: &Self::Device) {}

}```

Trait наследует множество других ops-traits (FloatTensorOps<Self>, IntTensorOps<Self> и т.д.), где реализованы конкретные операции (matmul, conv и пр.).

Реальные бэкенды (NdArray, Wgpu, LibTorch) реализуют этот trait.

**Пример:** Представьте, что у вас есть трейт Плавать:

```trait Плавать {

`    `fn плыть(&self);

}```

Любой тип, который хочет "уметь плавать", должен реализовать метод плыть. Например, Утка и Рыба могут реализовать этот трейт по-своему. Один трейт может "наследовать" другие трейты, то есть включать в себя их методы. Это значит, что если тип реализует "родительский" трейт, он автоматически должен реализовать и все "дочерние" трейты.

**Пример:** Если у вас есть трейт FloatTensorOps<Self>, который описывает операции для тензоров с плавающей точкой (например, умножение матриц), а ваш основной трейт Trait наследует его, то любой тип, реализующий Trait, должен уметь выполнять все операции из FloatTensorOps.

В дочерних трейтах (например, FloatTensorOps, IntTensorOps) описываются конкретные операции: умножение матриц (matmul), свёртка (conv) и другие. Это как набор инструментов для работы с данными.

**Пример:**

- matmul — это умножение матриц (как в математике).
- conv — это свёртка, которая часто используется в нейронных сетях для обработки изображений.

  Бэкенды — это конкретные реализации трейтов для разных библиотек или устройств. Они как "движки", которые выполняют операции на практике.

  **Примеры:**

  - **NdArray** — библиотека для работы с многомерными массивами на CPU.
  - **Wgpu** — библиотека для работы с графическими процессорами (GPU).
  - **LibTorch** — библиотека PyTorch для Rust, которая позволяет использовать вычислительные мощности PyTorch.

Если вы реализуете трейт Trait для NdArray, то все операции (matmul, conv и др.) будут выполняться с помощью этой библиотеки.

Представьте, что у вас есть трейт МатематическиеОперации, который наследует Сложение и Умножение. Реальные классы КалькуляторНаБумаге и КалькуляторНаКомпьютере реализуют этот трейт, но делают это по-разному: один считает вручную, другой — с помощью процессора.
#### **2. Определение модели generic над Backend**
Модели определяются как generic-структуры. Это позволяет одной модели работать на любом бэкенде.

`use burn::{

`    `module::Module,

`    `nn::{Linear, LinearConfig, Relu},

`    `prelude::\*,

`    `tensor::Tensor,

};

#[derive(Module, Debug)]

pub struct SimpleModel<B: Backend> {

`    `linear1: Linear<B>,

`    `linear2: Linear<B>,

`    `activation: Relu,

}

impl<B: Backend> SimpleModel<B> {

`    `pub fn forward(&self, x: Tensor<B, 2>) -> Tensor<B, 2> {

`        `let x = self.linear1.forward(x);

`        `let x = self.activation.forward(x);

`        `self.linear2.forward(x)

`    `}

}`

Более сложный пример (CNN из документации Burn):

`use burn::{

`    `nn::{

`        `conv::{Conv2d, Conv2dConfig},

`        `pool::{AdaptiveAvgPool2d, AdaptiveAvgPool2dConfig},

`        `Dropout, DropoutConfig, Linear, LinearConfig, Relu,

`    `},

`    `prelude::\*,

};

#[derive(Module, Debug)]

pub struct Model<B: Backend> {

`    `conv1: Conv2d<B>,

`    `conv2: Conv2d<B>,

`    `pool: AdaptiveAvgPool2d,

`    `dropout: Dropout,

`    `linear1: Linear<B>,

`    `linear2: Linear<B>,

`    `activation: Relu,

}

impl<B: Backend> Model<B> {

`    `pub fn forward(&self, images: Tensor<B, 3>) -> Tensor<B, 2> {

`        `let [batch\_size, height, width] = images.dims();

`        `let x = images.reshape([batch\_size, 1, height, width]);

`        `let x = self.conv1.forward(x);

`        `let x = self.dropout.forward(x);

`        `let x = self.conv2.forward(x);

`        `let x = self.activation.forward(x);

`        `let x = self.pool.forward(x);

`        `let x = x.reshape([batch\_size, 16 \* 8 \* 8]);

`        `let x = self.linear1.forward(x);

`        `let x = self.dropout.forward(x);

`        `let x = self.activation.forward(x);

`        `self.linear2.forward(x)

`    `}

}`

#### **3. Конфигурация модели и инициализация**
Используется Config для удобной инициализации:

`use burn::config::Config;

#[derive(Config, Debug)]

pub struct ModelConfig {

`    `num\_classes: usize,

`    `hidden\_size: usize,

`    `#[config(default = 0.5)]

`    `dropout: f64,

}

impl ModelConfig {

`    `pub fn init<B: Backend>(&self, device: &B::Device) -> Model<B> {

`        `Model {

`            `conv1: Conv2dConfig::new([1, 8], [3, 3]).init(device),

`            `conv2: Conv2dConfig::new([8, 16], [3, 3]).init(device),

`            `pool: AdaptiveAvgPool2dConfig::new([8, 8]).init(),

`            `activation: Relu::new(),

`            `linear1: LinearConfig::new(16 \* 8 \* 8, self.hidden\_size).init(device),

`            `linear2: LinearConfig::new(self.hidden\_size, self.num\_classes).init(device),

`            `dropout: DropoutConfig::new(self.dropout).init(),

`        `}

`    `}

}`

#### **5. Декораторы бэкендов (композиция)**
Burn позволяет "оборачивать" бэкенды для добавления функциональности:

```use burn::backend::{Autodiff, Fusion, Wgpu};

// Автодифференцирование + fusion на GPU

type TrainingBackend = Autodiff<Fusion<Wgpu<f32, i32>>>;

// Только inference на CPU

type InferenceBackend = NdArray<f32>;```

Это ключевой плюс Burn: один код — множество комбинаций (CPU/GPU, с/без autodiff, с fusion и т.д.).

# **Наследование**

В Rust **нет классического наследования,** Rust использует **traits** для достижения полиморфизма, повторного использования кода и абстракций. 

Traits могут "наследовать" друг друга через механизм **supertraits** (например, trait Child: Parent {}), что требует реализации родительского трейта. Это ближайший аналог наследования в Rust, и он активно применяется в библиотеках машинного обучения (linfa, tch-rs, tract, rust-bert, smartcore) для:

- **Исключения дублирования кода:** Если у вас много моделей, каждая из которых должна уметь обучаться и предсказывать, вы описываете это один раз в трейтах.
- **Гарантии компилятора:** Компилятор следит, чтобы вы не забыли реализовать все необходимые методы.
- **Гибкости:** Вы можете создавать иерархии трейтов, как в примере с linfa, где специализированные алгоритмы "наследуют" базовые возможности.

### **Основные способы использования "наследования" (через traits и supertraits) в интеграции Rust с ML**
1. **Иерархии трейтов для моделей и алгоритмов** (supertraits для "наследования" поведения) Определяют базовые трейты (например, Model или Algorithm), а производные трейты наследуют их требования. Пример: в библиотеке **linfa** (аналог scikit-learn) есть трейты вроде Fit, Predict, Transformer. Более специализированные алгоритмы (например, для кластеризации) "наследуют" базовые через supertraits, чтобы гарантировать наличие методов обучения и предсказания. Это позволяет строить иерархии без дублирования кода, аналогично OOP-наследованию.

   ```**trait Predict<X, Y> {**

   **fn predict(&self, input: X) -> Y;**

   **}**

   **trait Fit<X, Y>: Predict<X, Y> { // требует Predict**

   **fn fit(&mut self, data: X, targets: Y);**

   **}**

   **// Пример модели (в духе linfa)**

   **struct LogisticRegression;**

   **impl Predict<Vec<f64>, f64> for LogisticRegression {**

   **fn predict(&self, input: Vec<f64>) -> f64 { /\* ... \*/ }**

   **}**

   **impl Fit<Vec<Vec<f64>>, Vec<f64>> for LogisticRegression {**

   **fn fit(&mut self, data: Vec<Vec<f64>>, targets: Vec<f64>) { /\* ... \*/ }**

   **}**```

   Базовый трейт требует реализации, производный "наследует" его. Вы можете "прикрепить" трейты к своим структурам, реализовав для них требуемые методы.

1. **Trait objects для динамического полиморфизма в нейронных сетях**
 
 Используют dyn Trait для хранения разных моделей/слоёв в одном контейнере (например, векторе). **Trait object** — это способ работать с разными типами, которые реализуют один и тот же трейт, как с одним типом. Для этого используется ключевое слово dyn (от "dynamic" — динамический). В Rust нельзя создать вектор или другой контейнер, который хранит разные типы напрямую. Но можно хранить указатели на трейт-объекты, обёрнутые в Box (умный указатель, который выделяет память в куче). 

   `**let net: Vec<Box<dyn Layer>> = vec![**

   **Box::new(Linear::new()),**

   **Box::new(ReLU),**

   **];**`

   Здесь в одном векторе хранятся и Linear, и ReLU, потому что оба реализуют трейт Layer.

   Пример: в кастомных реализациях нейронных сетей (или в старых библиотеках вроде rusty-machine) определяют трейт Layer с методами forward и backward. Разные слои (Linear, ReLU, Conv) реализуют его. Сеть собирается как Vec<Box<dyn Layer>>, что имитирует наследование от базового класса Layer в OOP. Полезно для динамических архитектур (например, в inference-движках).

   ```**use tch::{Tensor, nn};**

   **trait Layer {**

   **fn forward(&self, xs: &Tensor) -> Tensor;**

   **}**

   **struct Linear { vs: nn::VarStore } // упрощённо**

   **struct ReLU;**

   **impl Layer for Linear {**

   **fn forward(&self, xs: &Tensor) -> Tensor {**

   **xs.linear(&self.weight, None) // пример из tch-rs**

   **}**

   **}**

   **impl Layer for ReLU {**

   **fn forward(&self, xs: &Tensor) -> Tensor {**

   **xs.relu()**

   **}**

   **}**

   **// Сеть как вектор слоёв**

   **let net: Vec<Box<dyn Layer>> = vec![**

   **Box::new(Linear::new()),**

   **Box::new(ReLU),**

   **];**```

   Храним разные типы в одном контейнере. 

   В нейронных сетях часто используются разные типы слоёв (линейные, активации, свёртки и т.д.). С помощью трейт-объектов можно собрать сеть из разных слоёв в одном контейнере и последовательно применять их к данным.

   `**let input = Tensor::randn(&[10], ());**

   **let mut output = input;**

   **for layer in net {**

   **output = layer.forward(&output);**

   **}**`

   Здесь входной тензор проходит через все слои сети по очереди.

1. **Generic bounds и trait inheritance для работы с данными/тензорами** Traits с supertraits ограничивают дженерики, чтобы код работал с разными типами данных. Пример: в **tch-rs** (bindings к PyTorch/libtorch) или **ndarray** трейты вроде Float или Numeric наследуются (например, f32: Float + std::ops::Add), позволяя писать generic код для разных точностей (f16, f32, f64). В ML это критично для оптимизации под CPU/GPU. Аналог: "наследование" поведения операций от базовых математических трейтов.

   `**fn train<M, D, T>(mut model: M, data: D, targets: T)**

   **where**

   **M: Fit<D, T> + Predict<D, T>, // "наследует" оба**

   **{**

   [**model.fit**](http://model.fit/)**(data, targets);**

   **let pred = model.predict(data);**

   **}**`

   Здесь M — это любой тип, который реализует трейты Fit и Predict. Функция train работает с любыми моделями, которые умеют обучаться (fit) и предсказывать (predict), независимо от конкретного типа данных. Код работает с любыми типами, реализующими нужные трейты.

   *Generic bounds*** это способ сказать компилятору: "Этот код работает не с любыми типами, а только с теми, которые удовлетворяют определённым условиям".

   `**fn print\_number<T: std::fmt::Display>(num: T) {**

   **println!("{}", num);**

   **}**`

   Здесь T: std::fmt::Display означает, что функция print\_number работает только с типами, которые можно вывести на экран (например, i32, f64, String).

   *Trait inheritance*** позволяет создавать "супертрейты", которые объединяют несколько трейтов.

   **trait Float: std::ops::Add + std::ops::Mul {}**

   *Super traits* позволяют группировать требования к типам.

   **trait Numeric: std::ops::Add + std::ops::Sub + std::ops::Mul + std::ops::Div {}**

   Типы, реализующие Numeric, должны поддерживать сложение, вычитание, умножение и деление.

   Благодаря дженерикам и трейтам можно писать код, который работает с разными типами, если они реализуют нужные трейты.

   В библиотеках для работы с тензорами (например, tch-rs — обёртка над PyTorch) часто используют трейты вроде Float или Numeric, чтобы код работал с разными числовыми типами (f16, f32, f64). Это важно для оптимизации под разные процессоры (CPU/GPU).

   **fn dot\_product<T: Numeric>(a: &[T], b: &[T]) -> T {**

   **a.iter().zip(b.iter()).map(|(x, y)| \*x \* \*y).sum()**

   **}**

   Эта функция работает с любыми числовыми типами, которые поддерживают умножение и суммирование.

1. **Композиция с трейтами вместо наследования** (composition over inheritance) Встраивают одну структуру в другую и делегируют поведение через трейты. Пример: в Rust-ML библиотеках (linfa, smartcore) модель может содержать поля вроде preprocessor: Box<dyn Transformer>, где Transformer — трейт. Это заменяет наследование базового класса препроцессинга, делая код более гибким и безопасным.

   ```**struct Pipeline {**

   **transformer: Box<dyn Transformer>,**

   **model: Box<dyn Predict<Vec<f64>, f64>>,**

   **}**

   **impl Pipeline {**

   **fn fit(&mut self, x: Vec<Vec<f64>>, y: Vec<f64>) {**

   **let x = self.transformer.transform(x);**

   [**self.model.fit**](http://self.model.fit/)**(x, y);**

   **}**

   **}**```

   Встраиваем трейты в структуру.

1. **Интеграция с внешними ML-фреймворками через FFI и трейты** Bindings к C/C++ библиотекам (libtorch, ONNX Runtime) оборачивают наследование из C++ в Rust-трейты. Пример: в **tch-rs** или **tract** (для ONNX) иерархии классов из C++ преобразуются в трейты и enum'ы в Rust, избегая прямого наследования.
### **Почему это лучше классического наследования в ML-контексте**
- **Безопасность и производительность** → Нет неожиданных override'ов, нулевых указателей или утечек.
- **Zero-cost abstractions** → Traits компилируются в статический диспатч (как инлайн-функции) или динамический (vtable), без overhead.
- **Гибкость** → Легко комбинировать поведение от нескольких трейтов (множественное "наследование").

# **Инкапсуляция**

Инкапсуляция в Rust реализуется через модификаторы видимости (pub, pub(crate), приватные поля по умолчанию в struct и impl), модульную систему и трейты. Это позволяет скрывать детали реализации, обеспечивать безопасность данных и предоставлять контролируемый интерфейс. В контексте ML инкапсуляция особенно полезна для создания безопасных, производительных и модульных компонентов, которые интегрируются с Python-экосистемой (PyTorch, TensorFlow, scikit-learn) или используются в чистом Rust.

Вот основные способы применения инкапсуляции Rust в интеграции с ML:

1. **Создание Python-расширений через PyO3 и maturin** Самый распространённый подход. Вы пишете производительные части ML-пайплайна (например, предобработку данных, кастомные слои нейросетей или inference) на Rust, инкапсулируя внутреннее состояние (тензоры, параметры модели) в приватных полях struct. Публичный интерфейс (методы) экспортируется в Python через атрибуты PyO3.

   Допустим, у вас есть функция для обработки больших массивов данных. На Python она работает медленно, а на Rust — в 10 раз быстрее. С помощью PyO3 вы "оборачиваете" Rust-код, чтобы его можно было вызывать из Python. В Rust вы создаёте структуру (struct), которая хранит внутри себя данные (например, тензоры или параметры модели). Эти данные скрыты от внешнего мира — их нельзя случайно испортить из Python. Чтобы защитить данные от ошибок (например, утечек памяти или неверного доступа). Python не знает, как правильно управлять памятью в Rust, поэтому лучше спрятать сложную логику внутри Rust-кода.

   **Пример:** У вас есть нейросеть. В Rust вы храните её веса в приватном поле структуры. Из Python можно только вызвать метод predict(), но нельзя напрямую изменить веса — это предотвращает ошибки.

   **Публичный интерфейс через PyO3 -** для того чтобы пользователи Python могли работать с вашим Rust-кодом, не зная его внутренней реализации.

   **Пример:** Вы пишете на Rust функцию extract\_features(), которая быстро извлекает признаки из данных. Через PyO3 вы делаете её доступной в Python как model.extract\_features().

   **Maturin -** инструмент, который помогает собрать ваш Rust-код в Python-пакет и опубликовать его на PyPI (как обычную библиотеку). Чтобы другим пользователям было легко установить и использовать ваш код через pip install.

   **Пример:** Вы написали расширение для ускорения работы с тензорами. С помощью maturin вы собираете его в пакет и публикуете. Теперь любой может установить его командой pip install ваш\_пакет.

   1. Преимущества инкапсуляции: скрытие сложной логики управления памятью Rust от Python-кода, предотвращение ошибок (например, утечек или неверного доступа к данным).
   1. Примеры использования: ускорение feature extraction, кастомные операторы в PyTorch/TensorFlow. Инструмент maturin упрощает сборку и публикацию как pip-пакета.
1. **Safe-обёртки вокруг FFI (Foreign Function Interface) с C/C++ библиотеками ML** Многие ML-фреймворки (libtorch от PyTorch, ONNX Runtime) имеют C/C++ API. В Rust вы создаёте обёртки: инкапсулируете unsafe FFI-вызовы в безопасных публичных методах, скрывая raw pointers и детали в приватных полях.

   FFI — это механизм, который позволяет программе на одном языке (например, Rust) вызывать функции, написанные на другом языке (например, C или C++).

   **Пример:** Представьте, что у вас есть мощная библиотека для работы с нейросетями, написанная на C++ (например, PyTorch). Вы хотите использовать её в программе на Rust. FFI позволяет Rust-коду "общаться" с этой библиотекой, вызывать её функции и получать результаты.

   В Rust есть понятие "unsafe" — это код, который не проверяется компилятором на безопасность. FFI-вызовы часто требуют использования unsafe, потому что Rust не может гарантировать безопасность кода на C/C++.

   Если вы вызываете функцию из C-библиотеки, которая работает с указателями (pointers), Rust не знает, что именно делает эта функция. Поэтому вы должны явно пометить такой вызов как unsafe.

   **Safe-обёртки -** это безопасные функции на Rust, которые внутри себя используют unsafe FFI-вызовы, но предоставляют пользователю безопасный интерфейс.

   **Пример:** Представьте, что у вас есть функция на C, которая принимает указатель на массив чисел. Вместо того, чтобы заставлять пользователя работать с сырыми указателями, вы создаёте функцию на Rust, которая принимает обычный вектор (Vec), а внутри уже сама преобразует его в указатель и вызывает C-функцию.

   **Инкапсуляция unsafe-кода -** это когда весь опасный (unsafe) код скрыт внутри модуля или структуры, а наружу выходит только безопасный API.

   **Пример:** Вы создаёте структуру Tensor на Rust, которая внутри хранит указатель на данные тензора из C-библиотеки. Все методы этой структуры (например, add, multiply) безопасны для пользователя, а работа с указателями происходит только внутри приватных методов.

   1. Библиотеки-примеры: tch-rs (bindings к libtorch), onnxruntime-rs.
   1. Инкапсуляция гарантирует, что наружу выходит только безопасный API, минимизируя риски при работе с GPU/тензорами.
1. **Разработка модульных компонентов в чистых Rust ML-фреймворках** Использование инкапсуляции для построения полноценных ML-библиотек на Rust без Python.

   Модульные компоненты — это отдельные, самостоятельные части программы, которые можно легко заменять, переиспользовать или обновлять, не ломая всю систему.

   **Пример:** Представьте конструктор Lego. Каждый кубик — это модуль. Вы можете собрать из них машину, а потом заменить колёса на гусеницы, не переделывая всю машину.

   **В Rust ML-фреймворках:** Модули могут быть отдельными алгоритмами (например, линейная регрессия, случайный лес), оптимизаторами, или даже поддержкой разных процессоров (CPU/GPU).

   Публичный API — это то, что видит пользователь (например, функции fit() и predict()). Внутренние детали — это то, как всё работает внутри (например, какие оптимизаторы используются, как хранятся данные).

   1. Примеры фреймворков:
      1. linfa (аналог scikit-learn) — инкапсуляция алгоритмов в трейтах и модулях для переиспользования.
      1. candle (лёгкий тензорный фреймворк, вдохновлённый PyTorch).
      1. burn (гибкий DL-фреймворк).
      1. tract (inference для ONNX-моделей).
   1. Инкапсуляция помогает разделять публичный API (fit/predict) от внутренних деталей (оптимизаторы, backend для CPU/GPU).
1. **Интеграция через WebAssembly (WASM)** Rust-код с инкапсулированными моделями компилируется в WASM для запуска в браузере или edge-устройствах. Скрываются детали модели (веса, архитектура) в приватных структурах, экспортируется только inference-API (только интерфейс для получения результатов работы модели (inference), а не сама модель). Веса — это параметры, которые модель научилась использовать для принятия решений. Архитектура — это её структура. В данном случае эти детали спрятаны, чтобы защитить интеллектуальную собственность или предотвратить взлом.
   1. Примеры: запуск моделей Hugging Face (через rust-bert или candle) в веб-приложениях без раскрытия реализации.
1. **Гибридные пайплайны: ускорение критических частей в существующих Python-проектах** Инкапсуляция позволяет заменять bottleneck-части (например, data loading, augmentation) на Rust-модули, сохраняя остальной код на Python. Через PyO3/rusty-numpy обеспечивается seamless интеграция с NumPy/Pandas массивами, при этом внутренние буферы и логика остаются скрытыми. 

   Это подход, при котором в одном проекте сочетаются два или более языков программирования. Например, основной код пишется на Python, а самые медленные (критические по скорости) части — на Rust.

   **Пример:** Допустим, у вас есть программа на Python, которая обрабатывает большие массивы данных. Часть кода, которая отвечает за загрузку и преобразование данных, работает слишком медленно. Вместо того чтобы переписывать весь проект на Rust, вы заменяете только эту медленную часть на Rust-модуль, а остальной код оставляете на Python.

   **Bottleneck (узкое место, тормозящая часть)** Это часть программы, которая работает значительно медленнее остальных и тормозит весь процесс. Например, функция, которая загружает данные с диска или обрабатывает большие массивы.

   **Seamless интеграция с NumPy/Pandas** Это значит, что Rust-модули могут работать с данными из NumPy и Pandas так, будто они написаны на Python. Вы передаёте массивы NumPy в Rust-функцию, она их обрабатывает и возвращает обратно — без лишних преобразований.

   **Пример:** Вы передаёте Rust-модулю массив NumPy, как если бы это была обычная Python-функция. Модуль быстро обрабатывает данные и возвращает результат обратно в Python, как будто ничего не произошло.
