# **Выходы модели (multi-task / разные задачи)**

Multi-task выходы — это MultiTaskOutput { policy, value, tree_value }, получаемый из общего backbone и трёх ветвей: Softmax-policy (2 действия), линейный value (1 скаляр) и опциональный DecisionTree.

 Один forward_multi_task закрывает и RL-действие, и оценку состояния, и auxiliary-предсказание — в духе Actor-Critic / multi-task сетей.


Модель решает несколько задач одним forward-проходом: выбор действия (policy), оценка состояния (value) и опционально предсказание дерева (auxiliary). Это классическая multi-task / Actor-Critic схема.

1. Структура результата: MultiTaskOutput

```
pub struct MultiTaskOutput {
    pub policy: Vec<f32>,        // [p_feed, p_play] после Softmax
    pub value: f32,              // скалярная оценка состояния
    pub tree_value: Option<f32>, // выход DecisionTree (если есть)
}

```

policy какую действие выбрать распределение (2 вероятности, сумма ≈ 1)

value насколько «хорошо» состояние регрессия (скаляр)

tree_value независимая оценка деревом скаляр или None

Один вызов → все головы сразу, без повторного прогона backbone.

2. Архитектура: shared backbone + heads

state (1)

    │

    ▼

Dense (layer1) → LayerNorm → ReLU

    │

    ▼

[layer_hidden...] → LayerNorm → ReLU   // зависит от ModelArchitecture

    │

    ├──────────────────┬──────────────────┐

    ▼                  ▼                  ▼

layer2_policy      layer_value      DecisionTree

Dense → Softmax    Dense → scalar   predict(state)

    │                  │                  │

    ▼                  ▼                  ▼

 policy            value            tree_value

В структуре сети:

```
pub layer1: DenseLayer,           // общий ствол
pub layer_hidden: Vec<DenseLayer>,
pub layer2_policy: DenseLayer,    // head: → 2
pub layer_value: DenseLayer,      // head: → 1
pub decision_tree: Option<DecisionTree>,
```

Shared representation (layer1 + hidden) извлекает признаки; task-specific heads решают разные задачи.

3. forward_multi_task — основной путь

```
pub fn forward_multi_task(&self, state: &[f32]) -> Result<MultiTaskOutput, AppError>

```

По шагам:

Валидация — пустой state → EmptyTensor; вне [0,1] → SpaceError.

Аугментации — только в Train.

Backbone — layer1 + все layer_hidden с LayerNorm + ReLU.
	
Policy head

```
let logits = self.layer2_policy.forward(&x)?;
let policy = softmax(&logits);  // [p_feed, p_play]

```

Value head
```
let value = self.layer_value.forward(&x)?[0];  // без Softmax

```

Tree auxiliary

```
let tree_value = self.decision_tree.as_ref().map(|t| t.predict(input_state[0]));
```

Сборка

```
Ok(MultiTaskOutput::new(policy, value, tree_value))

```


4. Совместимость: обычный forward

```
pub fn forward(&self, state: &[f32]) -> Result<Vec<f32>, AppError> {
    let multi = self.forward_multi_task(state)?;
    Ok(multi.policy)
}

```
Старый API (только policy) остаётся: внутри всё равно multi-task, наружу отдаётся лишь [p_feed, p_play]. Удобно для REINFORCE-циклов, которым value пока не нужен.

5. Как выходы используются

policy select_action, train_episode argmax → Feed/Play; log π для loss

value (задел Actor-Critic) оценка $V(s)$; сейчас в основном для multi-task API

tree_value логи / hybrid-архитектура интерпретируемый сигнал рядом с NN

Выбор действия:


```
pub fn select_action(&self, state: &[f32]) -> Result<Action, AppError> {
    let multi = self.forward_multi_task(state)?;
    Ok(if multi.policy[0] > multi.policy[1] {
        Action::Feed
    } else {
        Action::Play
    })
}
```

Обучение (reinforce_step) обновляет policy head (и backbone через градиенты). Value head в текущей версии при REINFORCE не обновляется отдельным value-loss — это упрощение; структура уже готова к A2C/PPO-подобному value_loss = (V − G)².

6. Зачем multi-task в RL

В Actor-Critic / PPO обычно:

Actor (policy) — $\pi(a\|s)$

Critic (value) — $V(s)$

Общий backbone экономит вычисления и улучшает признаки.

tree_value — дополнительный task (как auxiliary loss в multi-task learning): дерево даёт другой inductive bias и может помочь интерпретации.

7. Связь с архитектурами

ModelArchitecture меняет глубину backbone (hidden_sizes), но головы те же:

policy: последний hidden → 2

value: последний hidden → 1

HybridTreeNN явно подразумевает активное дерево; у других архитектур

decision_tree тоже может быть заполнен как auxiliary.

8. Схема полного выхода

obs → [aug?] → backbone → x_shared

                              │

              ┌───────────────┼───────────────┐

              ▼               ▼               ▼

         policy head     value head      DecisionTree

         Softmax           linear          predict

              │               │               │

              ▼               ▼               ▼

         MultiTaskOutput { policy, value, tree_value }

              │

              ├─→ select_action / env.step

              ├─→ log_prob → REINFORCE loss

              └─→ (будущий) value loss / logging
